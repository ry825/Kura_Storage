# テキスト表示・編集／ファイルバージョン 要求仕様書

## 1. 概要

UTF-8テキストファイルをAndroidアプリ内で表示・編集・保存できるようにし、楽観的更新競合を検出する。現在は内容変更番号としてだけ使われている`fileVersion`を、実際の過去内容を保持・一覧・取得・復元できるファイルバージョン機能へ拡張する。

## 2. 背景

正式仕様にはテキスト取得・保存と`expectedVersion`による競合検出が定義されているが、実装と過去内容の永続保持は未完了である。複数端末や共有利用者による編集で無条件上書きを防ぎ、誤編集後も内容を復元できる必要がある。

## 3. 前提条件と利用者

- 対象は厳密なUTF-8として読める最大1 MiBの`ACTIVE`なFileとする。
- 初回対応MIMEは`text/plain`、`text/markdown`、`text/csv`、`application/json`、`application/xml`、`application/yaml`とする。
- Ownerまたは現在`VIEWER`以上の利用者は表示でき、保存・復元は現在`EDITOR`以上の利用者だけが行える。
- `ADMIN` Roleだけを理由に他UserのFileへ暗黙アクセスできない。
- HDD上の現行ファイルを現在内容の正とし、過去版はKuraStorage管理領域へ不変データとして保持する。

## 4. 実装対象

### 4.1 テキスト表示・編集

- Androidで対応テキストを表示し、権限があれば編集モードへ切り替えられる。
- UTF-8 BOMは表示時に除去し、保存時はBOMなしUTF-8へ正規化する。
- 未保存状態、保存中、保存完了、競合、接続・権限・容量・文字コードエラーを区別する。
- 未保存状態で画面を離れる場合は確認し、Process再生成時は編集中内容を安全な上限内で復元する。
- 保存要求は取得時の`fileVersion`を`expectedVersion`として送り、現在版と異なる場合は`409 FILE_VERSION_CONFLICT`として無条件上書きしない。
- 競合時はサーバーの現在版を再取得して「再読込」「内容比較」「別名保存」を選べる。競合を無視する強制上書きは提供しない。

### 4.2 過去版保持

- Upload完了で初版を登録し、テキスト保存および外部内容変更で新しい版を作る。
- 名前変更・Move・Trash・Restoreだけでは新しい内容版を作らない。
- 各版にFile ID、version番号、内容、size、SHA-256、作成日時、変更契機、操作User／Device（存在する場合）を保持する。
- 現行内容を書き換える前に置換前内容を失わず、現行版と履歴metadataの公開を同一の回復可能な操作として扱う。
- 同一File内のversion番号は単調増加かつ一意とし、`FileEntry.fileVersion`と現行版を一致させる。
- 過去版内容は利用者APIから変更・個別削除できない。完全削除時はFileEntryと全過去版を同じ管理処理で削除する。

### 4.3 履歴表示・過去版取得・復元

- 現在閲覧可能な利用者は、版番号、更新日時、変更者の表示名または「外部変更」、size、checksumを新しい順でPage表示できる。
- 履歴閲覧時ごとに現在のFile権限と状態を再評価し、共有解除後は履歴metadataと内容を返さない。
- 過去版内容を取得して現在版と比較できる。
- 復元は対象過去版を現行内容へコピーし、復元前の現行内容も履歴として維持したまま新しい`fileVersion`を作る。過去のversion番号を再利用しない。
- 復元要求にも`expectedVersion`を必須とし、同時編集・外部変更・Move・Trash等との競合を安全に拒否する。

## 5. 受け入れ条件

- [ ] 対応MIME・UTF-8・1 MiB以下のFileをAndroidで表示できる。
- [ ] `EDITOR`以上は編集・保存でき、`VIEWER`は表示のみとなる。
- [ ] 未保存離脱確認と状態復元が動作する。
- [ ] 同じ版を基にした2端末の保存では一方だけが成功し、他方は409となり内容を失わない。
- [ ] Upload、テキスト保存、外部内容変更で実内容を持つ版が作られる。
- [ ] Rename・Moveだけでは`fileVersion`も履歴件数も変わらない。
- [ ] 履歴一覧と過去版内容取得が現在権限の範囲だけで成功する。
- [ ] 過去版復元により新しい版が作られ、復元直前の内容も再復元できる。
- [ ] Trash、`MISSING*`、Purge、共有解除、Device／Session失効時の動作が仕様どおりである。
- [ ] 書込失敗・DB失敗・電源断相当から、現行内容と`fileVersion`と履歴が矛盾なく回復できる。
- [ ] ファイル本文、過去版本文、物理PathをLog・監査ログ・Metric labelへ出力しない。
- [ ] LANとZeroTierの両経路、Android実機、PostgreSQL実体、実HDDで主要フローを確認する。

## 6. 成功指標

- 同一Fileへの競合保存で既存内容を無条件上書きする事象0件。
- 完了応答後に現行版または履歴内容が欠落する事象0件。
- 1 MiB上限の表示・保存・復元でAPI処理は通常2秒以内を目標とする。
- 新規の認可・競合・回復境界はLine Coverage 95%以上、Domain／Application全体は80%以上を維持する。

## 7. スコープ外

- 任意文字コードの自動変換、1 MiB超の編集、バイナリ差分、共同リアルタイム編集。
- 3-way merge、競合時の強制上書き、全文検索、Web UI。
- すべてのバイナリ形式を利用者が編集する汎用版管理。
- 利用者による版の個別削除、保持期間・世代数の設定UI。
